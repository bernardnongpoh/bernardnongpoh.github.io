Term Project Architecture

A C/C++ AI security-review & triage tool built from 10 independently-buildable components

Overview

The class-wide term project builds a C/C++-focused, execution-verified security-review and triage tool, spiritually similar to Arm Metis but specialized for C/C++ and grounded in real analysis + real execution. The substrate is ClangIR, the cross-TU story follows the Scalable Static Analysis Framework (SSAF) RFC, an LLM triages, and every finding surfaced to a human is verified by executing a sanitized PoC.

Ten groups (P1–P10) each own one component. Two bonus tracks (P11–P12) exist for teams that finish early. Every component is a standalone project: its own directory, its own build system, its own tests, its own CI. Groups depend on schemas and fixtures, not on each other's builds — you can ship, test, and demo your component against golden fixtures without a single other group being ready.

Shared contracts (C1–C10)

Every contract is a JSON Schema stored at contracts/<name>.schema.json. Every contract ships at least one canonical fixture at contracts/fixtures/<name>-*.json. The schemas are frozen at Progress Meeting 1; downstream components develop against fixtures, not upstream builds.

C2CIR module manifest + bitcodeP1P2, P3cir-manifest.schema.json; bitcode at artifacts/cir/*.cir.bc
C3Program model (functions, BBs, USRs, callgraph)P2P3, P4*, P7program-model.schema.json

A validator lives at tools/validate.py. Every component's CI runs validate.py on every output it produces against the relevant schema — a component that emits invalid JSON fails its own build, before integration.

Independence guarantees

Every component ships in isolation. Concretely:

  1. Own directory under components/p<N>/. Own build system (CMake / Cargo / Poetry / npm — whatever fits).
  2. A local Makefile exposing four standard targets:
    • make build — builds the component.
    • make test — runs unit tests against fixtures in contracts/fixtures/.
    • make demo — runs a scripted end-to-end on a canned input, produces a canonical output.
    • make validate — runs tools/validate.py on the demo output.
  3. No build-time dependency on peer components. At test time, inputs come from contracts/fixtures/. At demo time, inputs come from either fixtures or the component's own generated data.
  4. A component that consumes an upstream artifact must not read from a peer component's build/, target/, or in-memory objects. Read the artifact from a file, validated against the schema.
  5. A component that produces an upstream artifact must run make validate before declaring “done”. Invalid output = failing CI on the component's own repo.
  6. Integration is P12's job: integration/run-e2e.sh shells P1→P10 in sequence with real data. Individual components never call each other in-process.
  7. Every component publishes a small “usage” README at components/p<N>/README.md: what to install, what fixtures it expects, what it emits, one example command line.

Components (10 groups)

Build ingestion & ClangIR emission

P1
Get real OSS builds to hand us a compilation database and per-TU ClangIR bitcode.

Consumes

  • A cloned OSS source tree under sources/<project>/
  • config/build-<project>.yaml (target triple, flags, entry make/cmake targets)
For tests: contracts/fixtures/tree-hello.tar.gz (toy 3-file C project).

Produces

  • C1 — artifacts/build/compile_commands.json
  • C2 — artifacts/build/cir-manifest.json + artifacts/build/cir/*.cir.bc
Team size
3–4

Contract test

Build systems (make, cmake, ninja, kbuild); intercept-build; Docker

Auto-detect build system; incremental rebuild
Upstream impact
