HW-1 — LLVM & Coverage Instrumentation

Released Wed 12 Aug 2026 (during L9) · Due Fri 21 Aug 2026, 23:59 IST · Worth ~40 % of the HW component (i.e. ~4 % of the course grade)

Your first real contact with LLVM and Clang tooling. You will (1) write a source-level static-analysis tool over the Clang AST, (2) write an LLVM pass that instruments a program to record three coverage metrics at runtime, (3) compare against gcov and briefly discuss which coverage metric matters for fuzzing.

Everything you build here is a stepping stone for the term project. Take your time to understand the tooling instead of shortcutting.

Learning goals

  • Bootstrap and use the LLVM/Clang toolchain: clang, opt, llc, IR, passes.
  • Write a Clang libtooling RecursiveASTVisitor to walk C/C++ source.
  • Compute static software metrics (cyclomatic complexity, nesting depth) from the AST.
  • Write an LLVM ModulePass (new pass manager) that instruments IR.
  • Distinguish and implement function, basic-block, and edge coverage.
  • Design a compact runtime library and dump coverage on program exit.
  • Interpret coverage data on real programs and compare against a baseline (gcov).

Setup

  • LLVM version: LLVM/Clang 18.x on Linux (x86_64). Ubuntu 22.04 or 24.04 in a container is easiest; instructions in the docker/ starter folder.
  • Language: C++17 for the tools; C for the runtime; Python (optional) for report scripts.
  • Build system: CMake for the tools, plain Makefile for the runtime.
  • Starter repo: a template with a working “hello” Clang tool and a no-op LLVM pass will be linked from Teams the day HW-1 is released. Fork it, keep the layout, add your code.
  • Benchmarks (provided): three small C programs — sort.c (in-place sort), parser.c (tiny JSON tokenizer), hash.c (open-addressing hash table). Between them they exercise loops, recursion, and branching.

Part A · Clang AST tool (30 pts)

Build a Clang libtooling binary ast-metrics that takes one or more C/C++ translation units and emits a JSON report with static software metrics. Use clang::RecursiveASTVisitor.

For every function definition (skip declarations without bodies), report:

  1. name, file, line
  2. num_stmts — total statement count in the body
  3. num_basic_blocks — approximation: 1 + (# branch stmts) + (# early returns). Branch stmts include if, for, while, do, switch cases, && / ||, ternary.
  4. cyclomatic_complexity — McCabe: 1 + (# decision points).
  5. max_nesting_depth — deepest nested control structure.
  6. num_loops — for + while + do

Overall: total LOC, total functions, total loops, avg cyclomatic complexity.

Output format: single JSON to stdout.

{
  "translation_unit": "sort.c",
  "loc": 82,
  "totals": { "functions": 3, "loops": 5, "avg_cyclomatic": 4.33 },
  "functions": [
    { "name": "swap", "file": "sort.c", "line": 4,
      "num_stmts": 3, "num_basic_blocks": 1,
      "cyclomatic_complexity": 1, "max_nesting_depth": 0, "num_loops": 0 },
    { "name": "quicksort", "file": "sort.c", "line": 15,
      "num_stmts": 22, "num_basic_blocks": 8,
      "cyclomatic_complexity": 7, "max_nesting_depth": 3, "num_loops": 2 }
  ]
}

Hints:

  • Start from the Clang docs on RecursiveASTVisitor-based ASTFrontendActions.
  • To count decision points, override VisitIfStmt, VisitForStmt, VisitWhileStmt, VisitDoStmt, VisitSwitchStmt, VisitCaseStmt, VisitBinaryOperator (for &&/||), VisitConditionalOperator, VisitReturnStmt.
  • Track nesting with a stack that increments on entry and decrements on exit; keep a max.
  • Use clang::SourceManager to get file/line info.

Part B · LLVM coverage pass (50 pts)

Write an LLVM ModulePass named covpass using the new pass manager. When linked with your runtime library libcov.a, the resulting binary records three coverage metrics during execution and dumps them to coverage.json on exit.

Metrics to collect:

  1. Function coverage — bitmap indexed by function id; a bit is set the first time the function is entered.
  2. Basic-block coverage — bitmap indexed by (function id, block id).
  3. Edge coverage — hash-map from an edge id to a counter, where an edge id is a hash of (source_bb_id, dest_bb_id). Follow AFL's edge-coverage idea: at each block entry, XOR the previous block id with the current id, index into a 64K counter array. Increment saturating.

What the pass must do:

  • Assign each function a stable numeric id.
  • Assign each basic block a stable numeric id.
  • At the entry of each function, insert a call: __covrt_fn_enter(fn_id).
  • At the entry of each basic block, insert calls: __covrt_bb_enter(fn_id, bb_id) and __covrt_edge(bb_id). The runtime maintains a thread-local “previous block id”.
  • Register an atexit handler in the runtime that writes coverage.json.
  • Skip instrumenting functions your runtime itself defines (avoid infinite recursion).

Runtime library runtime/libcov.c:

  • Bitmaps sized to the number of functions/BBs at link time (or grow-on-demand with a mutex).
  • 64K-entry edge counter array (AFL-style).
  • On exit, walk the maps and print JSON. Also print a one-line human-readable summary to stderr:
    [covrt] functions: 12/15 bb: 47/62 edges: 118 time: 3.2 ms

Expected JSON:

{
  "program": "sort",
  "coverage": {
    "functions":   { "covered": 3,  "total": 3,  "pct": 100.0 },
    "basic_blocks":{ "covered": 14, "total": 18, "pct":  77.8 },
    "edges":       { "distinct": 21 }
  },
  "per_function": [
    { "name": "swap",      "bb_covered":  1, "bb_total": 1 },
    { "name": "quicksort", "bb_covered":  8, "bb_total": 9 }
  ]
}

Build & run: opt -passes=covpass input.bc -o instrumented.bc, then clang instrumented.bc runtime/libcov.a -o prog, then run ./prog.

Hints:

  • Use Writing an LLVM Pass as a starting point.
  • Insert callback declarations with M.getOrInsertFunction(…).
  • Use IRBuilder to insert calls at the start of each BB (respect PHI nodes: insert after them).
  • For the edge hash, thread-local “prev_id” must be initialised to 0 on function entry to avoid leaking edges across calls.

Part C · Comparison & discussion (15 pts)

Compile each of the three benchmarks two ways:

  1. With your covpass + libcov.
  2. With gcc --coverage to produce a gcov baseline.

In a 2-page report (report.pdf):

  • Report a table of covered/total functions, basic blocks, and (for your tool) distinct edges.
  • Report runtime overhead of your instrumented build vs. uninstrumented, and vs. gcov, on one benchmark.
  • Briefly answer: (a) When would edge coverage help a fuzzer more than block coverage? (b) Why AFL uses a 64K counter table instead of an exact edge map? (c) What information is lost in your bitmap encoding, and does it matter for fuzzing?

LLM policy

LLM use is allowed but bounded and logged. The point of the assignment is that you understand LLVM. If an LLM writes the interesting bits for you, the assignment loses its meaning — and the term project will be very rough.

Green (fine):

  • Looking up LLVM/Clang API syntax and correct includes.
  • Explaining error messages, linker errors, CMake warnings.
  • Boilerplate: build files, argument parsers, JSON printing.

Red (not allowed):

  • Prompting an LLM to write your RecursiveASTVisitor logic, your pass, or your runtime.
  • Copy-pasting an LLM's output as a whole file.
  • Undisclosed LLM use of any kind.

Include an LLM_USAGE.md in the repo listing every LLM session with a one-line topic (e.g. “Aug 15: asked Claude how to insert an IRBuilder call before PHI nodes”). Absence of this file means we assume no LLM use; if we find evidence of hidden LLM use, that's an academic-honesty case.
