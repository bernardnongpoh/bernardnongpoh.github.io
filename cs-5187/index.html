CS 5187 — Software Analysis

Monsoon Semester 2026 · 23 July – 12 November 2026 · Dept. of CSE, IIT Guwahati

A graduate course on static, dynamic, and hybrid program analysis and its use in finding bugs and vulnerabilities in real software. We cover foundations (soundness, precision, IRs), dataflow and abstract interpretation, pointer analysis, constraint-based analysis, type systems, symbolic execution, automated test generation, fuzzing, and modern LLM-assisted analysis. Lab work is built around LLVM, KLEE, and modern fuzzers.

Quizzes (10 %)

Two short in-class quizzes, closed-book, roughly 30–40 minutes, held during the regular lecture slot. Each quiz is worth 5 %. Quizzes are a sanity check on definitions, algorithms, and worked examples — not on the research readings.

Quiz 1
Wed 9 September 2026 · in-class during L21 · covers Topics 1–3 (Foundations, Testing, Dataflow). Held right before the mid-semester exam.
Quiz 2
Tue 10 November 2026 · in-class during L41 · covers Topics 4–8 (Pointer, Constraint-based, Types, SymExec, Test generation). Held right before the end-semester exam.

No make-up quizzes except in genuinely documented emergencies. If you miss one quiz for such a reason, its weight shifts to the other.

Term Project (25 %)

The project is where the course meets the real world. You'll pick a widely-used open-source target, build or adapt a program-analysis tool from the course, and try to find real bugs that get accepted upstream. Outcome is a short paper in FSE format with a reproducible GitHub artifact.

Internal weighting (of the 25 %)

Implementation & results
50 % — Does the analyzer find real vulnerabilities and generate successful exploits or fixes?
Full marks on this component require a bug accepted by upstream maintainers.
Progress meetings & final presentation
25 % — Can you present and explain your work? Evaluated across 3 progress meetings + the final presentation.
Report (FSE format)
25 % — Is the work clearly described and illustrated?

Team & individual accountability

  • Group size: up to 5 students. Solo and smaller groups allowed; expectations scale with team size.
  • Each member must justify their contribution (a signed statement in the report plus commit history in the repo).
  • At every progress meeting and at the final presentation, each member must be able to answer any question about any part of the project. “That was X's part” is not an acceptable answer.

Target open-source project

  • Must be widely used — think Linux kernel Chromium/V8 FFmpeg OpenSSL SQLite Postgres Node.js CPython LLVM and similar. Popular runtimes, browsers, kernels, media libraries, cryptography libraries, and databases are on-scope.
  • You cannot pick an obscure repo and simply point your tool at it. Rule of thumb: the project should have a large public user base and a functioning security / bug-triage process.
  • Get the target on the proposal so I can green-light it before you invest time.

Deliverables

  1. Proposal (2 pages): problem, target OSS project, technique, plan, team & role split. Sent to the instructor by 20 Sep 2026.
  2. Paper in FSE format: motivation, technique, implementation, evaluation, related work, threats to validity. Use the ACM Primary Article Template (LaTeX sigconf). PDF submitted with the artifact.
  3. Public GitHub repo containing:
    • Source code with a permissive license
    • README.md with build + run instructions, exact dependencies, and one-command reproduction of the headline result
    • Docker image or CI workflow that reproduces the evaluation from scratch
    • Bug reports / PRs / patches you filed upstream, linked with their state (open / acknowledged / merged)

What earns full marks on the “implementation” component

  • Your tool finds at least one real, previously-unknown bug in the target project and
  • The bug report / patch is accepted by upstream maintainers (merged PR, accepted CVE, or acknowledged advisory).
  • Partial credit is available for high-quality tooling and reproducible evaluation even if no bug lands; the ceiling on this component is capped without an upstream-accepted finding.
