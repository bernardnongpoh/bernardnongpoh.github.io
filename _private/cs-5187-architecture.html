Term Project Architecture

A C/C++ Cyber Reasoning System — ATLANTIS & MDASH-informed, scaled down for a semester

Overview

The class-wide term project builds a miniature Cyber Reasoning System (CRS) for C/C++. The design is patterned after Team Atlanta's ATLANTIS (winner of DARPA AIxCC final, Aug 2025 · $4 M prize · 43/70 vulns · 41/47 patches) and Microsoft's MDASH multi-model agentic security system (Taesoo Kim, VP Agentic Security, Microsoft — the same lead as ATLANTIS). The CRS goal is to autonomously find a PoV, prove it via sanitized execution, and fix it with a semantically-correct patch, bundled for upstream submission.

Eleven groups (P0–P10) each own one component. Three bonus tracks (P11–P13) exist for teams that finish early. Every component is a standalone project with a JSON-Schema contract, a Makefile with the four standard targets (build test demo validate), fixtures under contracts/fixtures/, and its own CI. Groups depend on schemas and fixtures, not on each other's builds.

Why a CRS and not a “SAST tool”. Modern winning vulnerability-discovery systems (ATLANTIS, MDASH, OSS-Fuzz-Gen) are fuzzing-first with LLM assistance and execution-based validation, not static-analysis-first with LLM triage. Static analysis serves to guide fuzzing (sinkpoint distance, reachability), and LLMs serve to synthesize inputs, harnesses, and patches — not to be the primary bug source. Our v4 architecture reflects this.

Industry requirements this system is designed to meet

  1. SARIF-first output so GitHub Code Scanning / Azure DevOps / GitLab / VS Code consume our findings.
  2. Incremental analysis on PRs (< 5 min on a PR touching < 1 % of code) via per-TU summaries + delta over the graph store.
  3. Low false-positive rate on delivered findings: only CONFIRMED PoVs reach the dashboard.
  4. Reproducible builds & scans with SLSA v1.0 provenance and CycloneDX SBOMs on every artifact.
  5. Runs on-prem, no code egress: local-LLM path via Ollama / vLLM by default; SaaS is opt-in.
  6. CI-native: one-command scan, SARIF upload, PR comments, issue filing.
  7. A minimized reproducer for every reported bug, in a format upstream maintainers accept.
  8. Deduplication at scale: fuzzers routinely produce 1000× duplicate crashes for one bug.
  9. Cross-language scaling story: C/C++ is the beachhead; ClangIR + graph DB leaves room for Rust/Java without a rewrite.
  10. Auditable triage decisions: LLM verdicts record model, prompt hash, and the code slice they saw.
  11. Budgeted LLM spend and rate limits: LiteLLM proxy, per-module RPM/TPM caps, graceful degradation when budget runs low (this is the reality — ATLANTIS spent $103K in one 12-hour final round).
  12. Fail-safe orchestration: no single-task failure cascades. Every task is idempotent and restartable.

Design v4 — what changed after studying AIxCC

The v3 of this page (a static-analysis-first SAST with LLM triage) was the wrong shape. Reading the full ATLANTIS technical report, the SoK on AIxCC, the Fuzzing Brain (4th place) paper, and Taesoo Kim's MDASH announcement, the following gaps became clear:

  1. Fuzzing is the primary bug source, not static analysis. ATLANTIS-C runs a Kafka-microservice ensemble of LibAFL + AFL++ + libFuzzer + a custom directed fuzzer (Bullseye) + a custom format-aware fuzzer, all sharing a corpus through an Ensembler that dedups seeds. Static analysis guides fuzzing (sinkpoint distance), it does not replace it.
  2. Patches are a first-class output (25 % of AIxCC score is Program Repair). ATLANTIS-Patch is a 5-agent framework (MARTIAN, MULTIRETRIEVAL, PRISM, VINCENT, CLAUDELIKE) coordinated by CRETE, plus a custom fine-tuned LLM trained via multi-turn GRPO on code-context retrieval. Our v3 had no patcher.
  3. An orchestrator is a subsystem, not a script. ATLANTIS's CP-MANAGER handles CP build, Azure/LLM budget allocation, PoV verification, stack-trace-based dedup, workflow across modules, and bundling for submission. Our v3 “P12 = shell scripts” was underspec'd by an order of magnitude.
  4. PoV, patch, and bundle are missing contracts. Our v3 contracts had finding / SARIF / verdict / cluster — but not the actual AIxCC-scored artifacts: PoV (harness id + crashing input + sanitizer signature + duration), patch (unified diff + affected file + build verified), bundle (PoV + patch + SARIF, submitted together for scoring bonus).
  5. Language specialization matters. ATLANTIS split into ATLANTIS-C (LibAFL / AFL++ / libFuzzer), ATLANTIS-Java (Jazzer + LibAFL-Jazzer + directed Jazzer), and ATLANTIS-Multilang (LLM-heavy cross-language MLLA agent). Multilang produced 64.4 % of verified PoVs in the final.
  6. Sinkpoint-directed fuzzing is a competitive advantage. ATLANTIS uses CodeQL-enhanced sink detection + static distance computation to build a directed fuzzer (Bullseye / directed Jazzer) that fuzzes toward known-dangerous API sites. Not a bonus — core.
  7. Multi-model debate for triage (MDASH). Microsoft runs SOTA auditor + distilled debater + independent SOTA counterpoint agents; disagreement between them raises finding credibility. Our v3 P6 was a single-model classifier.
  8. The last-mile / ExpKit gap. Fuzzers produce many non-scorable crashes (timeouts, OOMs, benign asserts). ATLANTIS built ExpKit to close the gap from crash to scorable vulnerability. We need a subsystem that says “this crash is a real memory corruption, this one is a timeout”.
  9. Budget management is a first-class subsystem. ATLANTIS's LiteLLM proxy centrally allocates LLM budget: 25 % to Patch, 37.5 % each to Multilang and C/Java. Per-module RPM/TPM limits prevent one module from starving another. On $50K/round.
  10. Fail-safe orchestration is a requirement, not a stretch. Task failures cannot cascade. Every module is a k8s pod with idempotent tasks, Redis for state, and web APIs for inter-module communication.

v4 keeps everything that survived critique — the industry requirements, the JSON+graph-DB contracts, KuzuDB-Vela as the graph store, the independence guarantees, milestones aligned with the course — and rebuilds the component list around the ATLANTIS pattern, scaled down for a semester and 55 students.

Scope reality-check. ATLANTIS was built by ~50 experts over 2 years with $100K/round. We can't rebuild it in a semester. What we can do is ship one working slice of the same shape: a multi-fuzzer ensemble on one or two OSS targets, a working PoV verifier + dedup, a multi-agent LLM triager and a 2-agent patcher against one CWE class. That's already a paper-worthy contribution.

Data model & storage

JSON contracts remain authoritative for CI, cross-component exchange, and fixtures. Large-scale artifacts (C2, C3, C4, C7, C9, C10, C11, C12) also materialize in an embedded graph DB so that cross-TU / cross-finding queries are graph traversals instead of bespoke code — this is how CodeQL, Kythe, and Ant Group's YASA all model this.

Pinned graph store: Vela Engineering's Kuzu fork (v0.12.0-vela, March 2026, MIT). Rationale: upstream kuzudb/kuzu was archived Oct 2025 after Apple's acquisition; the Vela fork adds concurrent multi-writer support, which we need because P3, P4, P5 all write findings and edges into the same graph store in parallel. Everything else from upstream (Cypher, vector search, FT search) is preserved. Bindings for Python / C++ / Rust / Go / Java / Node / WASM. Independent benchmarks: ~374× faster than Neo4j on multi-hop paths.

Isolation rule. Every component touches the DB only via tools/graph/adapter.py. Schema at tools/graph/schema.cypher. If the Vela fork stalls, we swap for DuckDB with a JSON blob column and recursive CTEs — JSON contracts are the source of truth, no component rewrite.

Independence guarantees

  1. Own directory under components/p<N>/. Own build system. Own Makefile with build test demo validate.
  2. Inputs come from contracts/fixtures/ at test time; DB via tools/graph/adapter.py; bus via tools/bus/.
  3. No in-process peer calls. Every cross-component signal is a JSON artifact + Kafka message + DB write.
  4. Every emitted artifact runs make validate against its JSON Schema + SARIF validator + provenance emitter.
  5. Integration lives in integration/run-e2e.sh. Owned by P12.
  6. Every component ships a README.md: install, fixtures, outputs, one example command.
