146 Bugs in Real Software: What My CS 5187 Students Found

Teaching
Software Testing
Fuzzing
Student teams in CS 5187 at IIT Guwahati tested more than 20 widely used open-source projects and reported 146 bugs upstream. 56 are already fixed.
Published

November 21, 2026

Modified

November 23, 2026

This is my first time teaching CS 5187 (Software Analysis), and I started the course with one belief: the best way to learn testing is to test software that people actually use. So the term project asked each team to pick a widely used open-source codebase, attack it with the techniques we covered in class, and report whatever they found to the maintainers.

The timing also helped. AI has sped up bug finding a lot. Language models can read an unfamiliar codebase, suggest where the risky code is, write test harnesses and input generators, and help turn a messy crash into a clean, minimal report. Work that used to take a team weeks of ramp-up now takes days. That let students who had never seen PostgreSQL or FFmpeg before reach the deep, interesting parts of these codebases within a single semester.

AI does not replace the method, though. A model will happily suggest a “bug” that is not one. What made the difference was pairing it with automatic checks, so every suggestion had to prove itself against the real program before anyone filed it.

The results came in better than I expected.

Where the bugs were

Databases dominate the list. That is partly because several teams chose them, and partly because a database is a good target for the kind of testing that does not need a crash to find a bug, which brings me to the most interesting result.

Most bugs were not crashes

When people hear “fuzzing” they picture a program falling over with a segmentation fault. Crashes were a small part of what the students found:

39%
Wrong results
Software runs fine but returns a wrong answer or writes a corrupted file.
32%
Memory safety
Out-of-bounds reads and writes, use-after-free, integer overflow, leaks.
19%
Crashes & assertions
Internal errors and failed sanity checks that abort the program.
10%
Resource exhaustion
Hangs and runaway memory use triggered by small inputs.

These shares come from the findings classified on 16 November. Most reports added since then are also wrong-result bugs, so that group has only grown.

Wrong results are the biggest group, and they are also the hardest to notice. A crash announces itself. A query that returns a plausible but wrong row count does not. Nobody files a bug report for an answer they never knew was wrong.

PostgreSQL: 11 fixes in a mature database. PostgreSQL is about as carefully engineered as open-source software gets. Students found queries that silently returned wrong results, and a bug where SQL-standard function bodies broke pg_upgrade. Several of the fixes were written by the students themselves and accepted into PostgreSQL.

llama.cpp: a flaw that hid for 31 months. The model-splitting tool could write a file that loads without complaint but is quietly wrong. Continuous fuzzing had missed it for more than two and a half years. A fuzzer only reports what its oracle can see, and “this output file is subtly wrong” is not something a crash detector can see.

FFmpeg: a 68 KB file asks for 1.7 GB. A tiny crafted video could make the demuxer request gigabytes of memory. This is fixed upstream, along with two seek bugs.

libarchive: a 1.8 KB ZIP asks for 4.2 GB. Three oversized-allocation bugs in archive reading, all fixed upstream.

Neovim: fixed the same day. A null pointer dereference in command parsing and a heap out-of-bounds read. The maintainers patched both within hours of the report.

Python type checkers: 24 reports across mypy, ty and pyright. Hangs on recursive types, unsound type narrowing and crashes. Five fixes have been merged so far.

libultrahdr: images it could not read back. The check was simple: the library must be able to decode what it just wrote. That exposed two bugs present in every release since v1.3.0, in a library OSS-Fuzz has fuzzed for more than two years. With the check turned off, 1.5 million executions found nothing. With it on, the first bug appeared after 34,400. One fix is merged and the other is in review.

LLVM and GCC: 14 reports against the coverage tools. Developers trust coverage reports to decide what has been tested. Students compared llvm-cov and gcov and found code reported as executed when it never ran, branches attributed to the wrong line, and lines dropped from the report. These reports are still open upstream.

How the bugs were found

None of the techniques are new. Each team took a well-established idea from the course and adapted it to their target.

  • Structure-aware input generation. Generate inputs that follow the target’s own grammar or file format, so the tests get past the parser and reach the deep logic behind it.
  • Consistency checks. Ask the same question in two equivalent ways. If the answers differ, at least one of them is wrong, and no crash is needed to prove it.
  • Differential testing. Run several tools that should agree (two compilers, two databases, three type checkers) and investigate every disagreement.
  • Sanitizer-instrumented fuzzing. Build the target with sanitizers so that silent memory errors become immediate, reproducible failures.
  • Round-trip checks. Write, read back, compare. This catches corruption in dumps, converters and file formats.
  • LLM assistance, checked automatically. Language models propose test cases, and only the ones that pass an automatic check are kept.

The first, second, third and fifth ideas all solve the same problem: they give the tester an oracle, a way to tell that an output is wrong without knowing the correct answer in advance. That is why the wrong-results category is so large. The students did not have better crash detectors than OSS-Fuzz. They had better questions.

Reporting bugs properly

Finding a bug is half the job. Getting it fixed is the other half, and maintainers are busy people. Before filing, every report was reproduced on a clean upstream build and minimised to the smallest input that still triggers it. A 68 KB reproducer with a one-line explanation gets attention. A 50 MB fuzzer output with a stack trace often does not.

The same-day Neovim fixes and the student-written PostgreSQL patches show what happens when the report makes the maintainer’s job easy.

Where things stand

As of 23 November 2026, 56 of the 146 reports are fixed upstream, either by a student patch or by the maintainers. Many of the rest are confirmed and waiting in review queues, so I expect that number to keep growing. Security-sensitive findings that are not yet public or patched are not listed here and will stay unlisted until a fix ships.
