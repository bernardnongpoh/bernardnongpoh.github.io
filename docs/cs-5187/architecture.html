Term Project Architecture

Building a C/C++ AI security-review & triage tool from student components

Overview

The class-wide term project is to build a C/C++-focused, execution-verified security-review and triage tool, spiritually similar to Arm's Metis, but specialized for C/C++ and grounded in real analysis instead of LLM opinions alone. The analysis substrate is ClangIR, the cross-TU organization follows the Scalable Static Analysis Framework (SSAF) RFC on LLVM Discourse, and every finding surfaced to a human is verified by executing a program — not just by an LLM's confidence score.

Ten student groups (P1–P10) each own one component. Two bonus tracks (P11–P12) exist for teams that finish early or want a cross-cutting concern. The components share stable JSON / SARIF interfaces so they can be developed independently and stitched together at the end of the semester.

Why this shape

  • ClangIR preserves C/C++-level types and operations that LLVM IR throws away — better precision for security analyses without doing your own frontend.
  • SSAF gives us a principled cross-TU organization: per-TU summaries, USR-keyed entities, and an offline linker. Avoids ASTImporter and scales to large open-source targets.
  • LLM triage filters analyzer noise, but LLM alone is not evidence — hence the execution verifier.
  • Execution verifier runs sanitized PoCs so “this is a bug” means “we made it crash on your box, here's the reproducer.”

Components (10 groups)

Team size hints assume up to 5 students, per the project rules. Every component's upstream-bug expectation is spelled out under “Definition of upstream impact” because not every component finds bugs directly — some enable other components to.

Build ingestion & ClangIR emission

P1
Get real OSS builds to hand us a compilation database and per-TU ClangIR bitcode.
Team size
3–4
Prereq skills
Build systems (make, cmake, ninja, kbuild); intercept-build; Docker
Depends on
—
Provides
compile_commands.json + *.cir.bc per TU; a build recipe for each target project
Deliverable
Scripts & Dockerfiles that build 3 target OSS projects (start with SQLite, Nginx, FFmpeg) and dump the CIR

Auto-detect build system; incremental build support so re-analysis is fast
Upstream impact
Not directly; enables every downstream stage

LLM-based triage layer

Team size

Depends on

Execution-based verifier

P8
Compile P7's harness with ASan/UBSan/MSan, run it, optionally fuzz and/or concolic-execute. Emit a verdict backed by a real crash log.
Team size
4–5
Prereq skills
Sanitizers, LibFuzzer/AFL++, KLEE / SymCC, container isolation
Depends on
P5, P7
Provides
Sandbox that runs harnesses with a time budget; verdicts: CONFIRMED, REJECTED_BY_EXECUTION, INCONCLUSIVE; attaches sanitizer log, minimized crash input, build recipe
Deliverable
End-to-end run on findings from at least one P4* detector, showing precision improvements vs. taking the detector's word
Stretch

Upstream impact
Yes (jointly with a P4*) — a confirmed crash + minimized input is exactly what upstream maintainers accept

Integration plan

  • Everyone works in the same GitHub org under one monorepo (or a small set of coordinated repos linked as submodules). Instructor pre-creates the org and gives every group a subdirectory + write access.
  • Interfaces are frozen at Progress Meeting 1 (Oct 5–9). The JSON schemas for CIR modules, summaries, findings, and verdicts are the contract; anything private inside a component can evolve freely.
  • Every component ships a mock in its first week so downstream components aren't blocked. If P4a hasn't emitted a real finding yet, P5 consumes a canned finding.json to keep integrating.
  • The class-wide integration checkpoints are the three project progress meetings and the final presentation.
  • Every group's report chapter is written against the same LaTeX skeleton (P12 provides). The final “paper” is really N chapters — each group can still submit its own individually-graded report per project rubric.

References

  • Arm Metis — AI-powered security code-review framework (Python, Tree-sitter, LLM-driven). Model to learn from but not copy: we specialize on C/C++ and verify by execution.
  • RFC: Scalable Static Analysis Framework — the SSAF blueprint for per-TU summaries, USR-keyed entities, and cross-TU linking.
  • ClangIR (CIR) — MLIR-based high-level IR for C/C++ preserving language-level types and operations.
  • SARIF v2.1.0 — the finding format everyone in the pipeline consumes / emits.
  • NIST SARD / Juliet — labeled C/C++ CWE test cases for measuring detector precision/recall.
  • OSS-Fuzz — harness & sanitizer conventions we borrow for P7/P8.
  • LibFuzzer, KLEE — the two execution engines P8 defaults to.
