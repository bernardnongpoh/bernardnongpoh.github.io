Term Project Architecture

Build a C/C++ AI security-review & triage tool that industry can actually use

Overview

The class-wide term project builds a C/C++-focused, execution-verified security-review and triage tool. It is spiritually similar to Arm Metis but specialized for C/C++, grounded in real analysis over ClangIR, organized by the SSAF RFC, triaged by an LLM in the style of IRIS / LLift, and verified by executing a sanitized PoC in the style of OSS-Fuzz / OSS-Fuzz-Gen.

Ten groups (P1–P10) each own one component. Two bonus tracks (P11–P12) exist for teams that finish early. Every component is a standalone project: its own directory, its own build system, its own tests, its own CI. Groups depend on schemas and fixtures, not on each other's builds — you can ship, test, and demo your component against golden fixtures without a single peer being ready.

Industry requirements this system is designed to meet

Read this section before proposing scope. If your component doesn't satisfy at least one of these industry requirements, cut it. If you want to add scope, tie the addition to a specific requirement.

  1. SARIF-first output. Every finding surfaces as SARIF v2.1.0 so GitHub Code Scanning, Azure DevOps, GitLab, VS Code, and every serious enterprise SAST dashboard can consume it. Anything else is gravy.
  2. Incremental analysis on PRs. Enterprise CI needs answers in < 5 min on a PR touching < 1 % of the code. This is the Szabó et al. “Incrementalizing Production CodeQL Analyses” (ESEC/FSE 2023) problem — solve it with per-TU summaries + a delta over the SSAF store, not full re-scan.
  3. Low false-positive rate on delivered findings. Meta's public Infer numbers say devs stop fixing when FPR passes ~20 %. Our answer: triage with an LLM (P6) and confirm with sanitizer execution (P8). Only CONFIRMED or high-confidence findings reach the dashboard.
  4. Reproducible builds & scans (SLSA / in-toto). Every artifact carries provenance so a regulator or downstream consumer can replay it. This is table stakes for federal / finance / healthcare in 2025+.
  5. Runs on-prem, no code egress. The default triage path uses a local LLM (Ollama / vLLM); the SaaS path is opt-in. No enterprise will let source code leave the perimeter without controls.
  6. CI-native. One-command scan, exits 0/1, comments on the PR, uploads SARIF, opens issues. GitHub Actions + GitLab CI examples ship in P12.
  7. Reproducer for every reported bug. Upstream maintainers (Linux, Chromium, FFmpeg, OpenSSL) only accept reports with a minimized crashing input. That's exactly what P8 emits.
  8. Deduplication at scale. Fuzzers routinely emit thousands of crash reports for one bug. A production tool that shows 1,000 duplicates gets uninstalled. P9 owns this.
  9. Cross-language scaling story. C/C++ is the beachhead. But the architecture must not preclude Rust / kernel-eBPF / drivers. ClangIR + SSAF gives us a plausible path to that.
  10. Auditable triage decisions. When an LLM says “this is a false positive,” the rationale, the code slice it saw, and the model version are recorded (C7). No black-box “trust the AI.”

Data model & storage

JSON contracts alone don't scale to Linux-kernel-sized inputs (30 M+ LOC, millions of basic blocks). We adopt a hybrid model that is standard in production SAST (CodeQL uses a Datalog-oriented relational DB; Kythe uses a graph protobuf store; Ant Group's YASA uses a unified AST DB):

  • JSON contracts (C1–C10) stay authoritative for schemas, fixtures, and cross-component exchange. This is what CI validates and what humans diff.
  • An embedded graph DB materializes the same data for query performance. Every entity has a stable ID; every finding links back to a code entity; every verdict links back to a finding. Cross-TU queries become graph traversals instead of custom code.

Concrete choice: Vela Engineering's Kuzu fork

We pin the class-wide graph store to Vela Engineering's Kuzu fork (v0.12.0-vela, March 2026 · MIT-licensed). Rationale:

  • Original KuzuDB was archived Oct 2025 after Apple's acquisition of Kuzu Inc. Depending on the abandoned upstream is not safe for a semester project or an industry-facing artifact.
  • Concurrent multi-writer support is the fork's headline addition — exactly what we need. Our four detectors (P4a–P4d) all write findings and analysis edges into the same graph store simultaneously. Stock Kuzu serialized writes; the Vela fork lets us run detectors in parallel without contention.
  • Everything else from upstream is preserved: full Cypher, vector search, full-text search, MIT licence.
  • Performance vs Neo4j (independent benchmarks): ~374× faster on multi-hop path queries (0.009s vs 3.22s on 100K nodes / 2.4M edges), ~18× faster bulk ingest. Cross-TU call-graph traversals in P4* / P9 stay under 100 ms even on Linux-kernel-scale program models.
  • Bindings for Python, C/C++, Rust, Go, Java, Node, WASM — every group's language is covered. Zero-infra embedded runtime, so no server to fight in Docker.
Isolation rule. Every component depends on the DB only via tools/graph/adapter.py (thin adapter). Adapter defines the entity + edge schema in tools/graph/schema.cypher and exposes a tiny API: insert_node(), insert_edge(), query(). If the Vela fork ever stalls, we swap the adapter's backend for DuckDB with a JSON blob column + recursive CTEs — the JSON contracts remain the source of truth, so no component needs rewriting.

Graph schema (Cypher, sketch)

// Nodes (:TranslationUnit {tu_id, path, hash}) (:Function {usr, name, file, line, tu_id}) (:BasicBlock {bb_id, function_usr, index}) (:Value {value_id, function_usr, kind}) // SSA values in ClangIR (:Summary {kind, function_usr, payload_hash}) (:Finding {finding_id, cwe, severity, detector, sarif_ref}) (:Verdict {finding_id, status, sanitizer, log_hash}) (:Cluster {cluster_id, representative_finding_id}) // Edges (:Function)-[:IN_TU]->(:TranslationUnit) (:BasicBlock)-[:IN_FUNCTION]->(:Function) (:Function)-[:CALLS {call_site}]->(:Function) (:Value)-[:DEFINES]->(:Value) // def-use (:Value)-[:FLOWS_TO {via}]->(:Value) // taint / dataflow (:Summary)-[:OF]->(:Function) (:Finding)-[:LOCATED_AT]->(:Function)|(:BasicBlock) // provenance (:Verdict)-[:CONFIRMS]->(:Finding) (:Cluster)-[:CONTAINS]->(:Finding)

Alternatives considered

  • Plain JSON files — simple; blows up on large targets; no cross-TU query.
  • SQLite — ubiquitous, but graph queries are painful; recursive CTEs don't scale to k-hop reachability over M edges.
  • DuckDB — excellent columnar; no native graph; usable as a fallback if the Kuzu fork falters.
  • Neo4j embedded — GPL licence issues + heavy JVM.
  • Datalog engine (Soufflé) — matches CodeQL's model; steeper student ramp; students already meet Datalog in L25 so a stretch team can layer this on top of KuzuDB.
Rule of thumb: If your component only touches thousands of entities, JSON is fine. If it touches millions, go through KuzuDB. P5 & P10 read via SARIF and DB queries; P1–P4* & P8–P9 write into both.

Independence guarantees

  1. Own directory under components/p<N>/. Own build system.
  2. Each component has a Makefile exposing make build test demo validate. Fixtures come from contracts/fixtures/.
  3. No build-time dependency on peer components. No in-process cross-calls.
  4. The graph DB is accessed via tools/graph/adapter.py. Components read via JSON or DB. Both are the same data.
  5. Every produced artifact runs make validate which invokes JSON-Schema + SARIF validators + tools/provenance.py.
  6. Integration is P12's job (integration/run-e2e.sh).
  7. Every component ships a README.md: install, fixtures, outputs, one example command.
